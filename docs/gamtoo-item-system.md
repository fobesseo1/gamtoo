## 1. 현재 앱 현황

- **앱 이름**: 감투 ("감탄 to me"의 줄임말)
- **한 줄 정의**: 하루의 작은 감탄을 기록하고 포스터로 남기는 앱
- **스택**: Next.js + Supabase + Vercel
- **배포**: https://gamtoo365.vercel.app

### 화면 구성

```
기록하기 │ 보관함 │ 감투 │ 내 캐릭터
```

| 탭 | 경로 | 내용 |
|---|---|---|
| 기록하기 | `/make` | 사진(선택), 문구(선택 40자), 위치(선택) → 포스터 생성 |
| 보관함 | `/archive` | 내가 만든 **포스터** 목록 |
| 감투 | `/collection` | **도감** ↔ **내 감투** 내부 전환 |
| 내 캐릭터 | `/profile` | 메인 캐릭터 선택 |

- 문구 미입력 시 기본값 `I amaze myself.`
- 위치 미입력 시 기본값 `Seoul, Myeong-dong`

### 기록 흐름

```
입력 → 축하 애니메이션("나에게 감탄!") → 포스터 완성
     → [저장하기] → 로그인(미로그인 시) → 감투 획득 리빌
```

- **다운로드**는 로그인 없이 가능
- **저장하기** 시점에 로그인을 요구한다. 결과물을 먼저 보여준 뒤 요청해야 이탈이 적다
- 감투 리빌이 축하 애니메이션이 아니라 저장 성공 직후에 뜨는 이유:
  감투는 `post_id`가 필요한데, 그 값이 저장 성공 시점에야 생기기 때문

## 2. 시스템 개요

### 2.1 설계 원칙

이 앱의 본질은 **자기칭찬(내적 동기)** 이다. 보상이 **행동의 대가**가 아니라
**행동의 흔적(기념품)** 으로 읽혀야 한다.

> 보상이 행동의 이유가 되면 안 되고, 행동의 증거여야 한다.

이 원칙에서 파생되는 실무 규칙:

- **기록하면 무조건 뭐라도 준다.** 빈손으로 돌아가는 경험을 만들지 않는다
- 하루에 여러 번 기록하는 것은 좋은 일이 여러 번 있었다는 뜻이다. **막지 않는다**
- 보상을 조이는 제약(횟수 제한 등)은 필요해지면 그때 넣는다. 미리 넣지 않는다

### 2.2 두 가지 축적물

| | **감탄** | **감투** |
|---|---|---|
| 성격 | 숫자 카운터 | 수집품(모자) |
| 지급 | 기록 저장 시 항상 +1 | 기록 저장 시 지급 |
| 중복 | 개념 없음 (그냥 숫자) | **중복 허용. 쌓인다** |
| 현재 용도 | 누적 표시 | 도감 + 보관 |
| 향후 용도 | **소모 재화 후보** (미정) | 분해/교환 대상 (미정) |

**지금은 `기록 수 = 감탄 수 = 감투 수` 로 전부 같아도 무방하다.**
나중에 감투 쪽에 제약이 붙거나 감탄에 소모처가 생기면 자연히 갈라진다.
그때를 위해 둘을 별개 개념으로 유지한다.

### 2.3 감투 지급 조건

| 조건 | 현재 상태 |
|---|---|
| 사진 포함 기록만 | **적용 중** |
| 하루 횟수 제한 | **없음** |

- **하루 1회 제한은 제거되었다.** 되살리지 말 것
- `profiles.last_drop_date` 컬럼은 남아 있으나 **판정 로직에서 참조하지 않는다**
- 향후 유저 규모가 커지면 횟수 상한 등을 검토할 수 있다.
  그때는 카운터 컬럼을 새로 추가하면 되며, 소급 처리가 필요 없으므로 미리 만들지 않는다

## 3. 에셋 규격 (2026-07-27 개정 — 2D 라인아트 캐릭터 교체 반영)

> "얼굴 원 cx=135 cy=135 r=135" 규칙은 **폐기**되었다. 3D 클레이 시절 캐릭터는
> 실제로 완전한 원이었지만, 2D 라인아트 캐릭터는 손그림 blob이라 캐릭터마다
> 얼굴 비율이 다르다 (물범은 넓적, 아기곰은 동그람 등). 중심 좌표를 억지로
> 맞추면 오히려 머리 꼭대기 위치가 캐릭터마다 어긋나 모자가 제각각으로
> 얹힌다 — 모자는 "얼굴 중심"이 아니라 "머리 꼭대기"에 앉기 때문이다.
> 아래는 그 대체 규칙이다.

### 3.1 공통 좌표계

```
viewBox : "0 -100 270 370"   ← 캐릭터/아이템 전부 동일
상단 여유: y = -100 까지 (모자 위쪽 장식이 솟는 공간)
```

**절대 좌표를 딱 맞추는 게 아니라, 아래 범위 안에만 들어오면 된다:**

- 얼굴 가로폭은 270에 거의 꽉 차게 (좌우 여백 거의 없이)
- **얼굴(턱) 최하단이 y=270** — 정렬 기준점은 이거 하나뿐이다
- 머리 위쪽은 캐릭터마다 달라도 된다. 귀·더듬이 같은 부속물이 y=0보다
  위로, 심하면 -100 근처까지 솟아도 정상이다 (예: 모찌 더듬이)
- 모자 하단 기준선은 **y=80** (겹침 비교 결과 채택 — 3.1.2 참조).
  상단은 y=-100을 넘지 않게

> **왜 머리 꼭대기가 아니라 턱 밑을 기준으로 잡았나**: 처음엔 "머리 꼭대기
> = y=0"으로 정렬했는데, 캐릭터마다 귀·더듬이 유무가 달라서 "머리 자체"가
> 어디까지인지 매번 판단해야 했다. 그 판단을 잘못한 모찌(더듬이 끝을
> 머리끝으로 잘못 잡음)에서 왕관이 얼굴을 파고드는 문제가 실제로 발생했다.
> 반면 **턱 밑(얼굴 최하단)은 캐릭터 수만큼 있는 게 아니라 항상 하나뿐**이라
> 헷갈릴 여지가 없다. 그래서 기준을 턱 밑으로 바꿨다.

### 3.1.1 캐릭터별 실제 적용 값 (참고 — 새 캐릭터 추가 시 이렇게 실측할 것)

Figma 원본은 viewBox `"0 0 270 370"`으로 나오므로, 각 캐릭터의 얼굴(턱)
최하단 bbox bottom을 실측해서 **그 값이 270이 되도록**
`<g transform="translate(0, -N)">`로 이동시켰다.

| 캐릭터 | 원본 얼굴 bottom y | 적용 이동값 | 결과 bottom y | 결과 top y (참고) |
|---|---|---|---|---|
| 물범 seal | 366.8 | -97 | ~270 | 28 |
| 판다 panda | 367.0 | -97 | ~270 | 14 |
| 비숑 bichon | 367.0 | -97 | ~270 | 27 |
| 아기곰 bear | 366.5 | -96 | ~270 | 5 |
| 모찌 mochi | 367.0 | -97 | ~270 | -34 (더듬이 포함, 정상) |

턱 밑 기준으로 재보니 5종 이동값이 -96~-97로 거의 균일했다 (머리 꼭대기
기준일 땐 -63~-125로 캐릭터마다 크게 달랐던 것과 대조적) — 얼굴 아랫부분은
디자이너가 원래 아트보드 하단에 맞춰 그렸기 때문으로 보인다. 결과 top y는
캐릭터마다 다르며 (모찌는 더듬이 때문에 음수), **이건 정상이고 보정 대상이
아니다.**

### 3.1.2 모자 겹침 기준 (y=80)

모자 하단이 y=40이었을 때는 얼굴 지름(270) 대비 겹침이 15%뿐이라 "얹혀만
있고 쓴 느낌이 안 남" 문제가 있었다. **y=80 (겹침 약 30%)로 변경** —
5종 캐릭터에 왕관을 씌워 40/60/80 세 단계를 나란히 비교한 뒤 채택한 값이다.

- 기존 모자 7종(`hat_beanie`, `hat_crown`, `hat_jokduri`, `hat_cap`,
  `hat_straw`, `hat_bucket`, `hat_party`) 전부 내부 좌표를 그대로 두고
  `<g transform="translate(0, 40)">`로 감싸서 일괄 적용했다 (형태 변경 없음)
- **앞으로 새로 그리는 모자도 이 기준(하단 y=80)에 맞춰 그릴 것**

### 3.2 합성 방법

**좌표 변환, 스케일 계산, 앵커 오프셋 테이블이 전부 불필요하다.**
동일 viewBox를 공유하므로 그냥 겹치기만 하면 된다.

```jsx
<svg viewBox="0 -100 270 370">
  <CharacterSvg />   {/* 아래 레이어 */}
  <HatSvg />         {/* 위 레이어 */}
</svg>
```

- 모자가 귀나 더듬이를 일부 가리는 것은 **의도된 동작**이다. 보정하지 말 것
- 캐릭터별 개별 조정 로직을 만들지 말 것

### 3.3 파일 목록

**캐릭터** (`char_*.svg`) — 물범 `seal`, 판다 `panda`, 비숑 `bichon`, 아기곰 `bear`, 모찌 `mochi`

**모자** (`hat_*.svg`)

모자 하단 기준선이 y=40 → y=80으로 바뀌면서 (3.1.2) 아래 상단/하단 y도
전부 +40 됐다. 내부 좌표(path의 `d` 등)는 안 건드리고 `translate(0,40)`
래퍼로만 이동시켰다.

| 파일 | 이름 | 색상 | 상단 y | 하단 y | 상태 |
|---|---|---|---|---|---|
| `hat_beanie.svg` | 비니 | 변수형 | -43 | 82 | 제작 완료, **앱 미적용** |
| `hat_crown.svg` | 왕관 | 고정 | -46 | 82 | **적용 중** |
| `hat_jokduri.svg` | 족두리 | 고정 | -16 | 80 | **적용 중** |
| `hat_cap.svg` | 야구모자 | 변수형 (팔레트 미정) | -17 | 82 | **적용 중** |
| `hat_straw.svg` | 밀짚모자 | 변수형 (팔레트 미정) | -6 | 88 | **적용 중** |
| `hat_bucket.svg` | 버킷햇 | 변수형 (팔레트 미정) | 6 | 82 | **적용 중** |
| `hat_party.svg` | 파티 고깔 | 변수형 (팔레트 미정) | -56 | 78 | **적용 중** |

### 3.4 SVG id 규칙 (필수)

- 모든 gradient/filter id는 **파일 간 고유**해야 한다
- 현재 45개 id 전부 고유함이 검증됨
- **새 에셋 추가 시 반드시 접두어를 붙일 것** (`hat_gat.svg` → `gatBody`, `gatBrim`)
- 이유: 여러 SVG를 인라인으로 동시 렌더할 때 id가 겹치면 브라우저가
  문서 전체에서 첫 번째 정의를 찾아 쓴다 → 물범 그라디언트가 아기곰에 적용되는 식으로 깨진다

### 3.5 색상 변수 (변수형 모자 전용)

```css
--hat-base   /* 기본색 */
--hat-light  /* 밝은 면 */
--hat-dark   /* 어두운 면 */
```

- 각 변수에 폴백값이 있어 미주입 시에도 렌더된다
- **모자는 반드시 인라인 SVG로 렌더할 것.** `<img src>`나 CSS 배경으로 넣으면
  외부 CSS 변수가 주입되지 않아 색상 변경이 동작하지 않는다
- `base` 하나에서 `light`/`dark`를 계산해 파생시키는 구조를 권장

캐릭터 얼굴색도 같은 방식이다 — `CHARACTER_FACE_COLORS`
(`src/lib/characters/constants.ts`)를 `CharacterWithHat`이 루트 `<svg>`에
`--face-color`로 주입한다. 캐릭터가 5종 고정, 색도 캐릭터당 1개뿐이라
DB 테이블 없이 프론트 상수로 둔다 — 나중에 유저가 색을 직접 고르는 기능이
생기면 그때 `profiles`에 컬럼 하나 추가하면 되고, 지금 미리 만들 이유가
없다 (소급 처리할 기존 데이터가 없으므로).

### 3.6 확장 여지 (지금 구현하지 않음 — 구조만 남겨둠)

- **부위별 색상 변수**: 얼굴색뿐 아니라 귀 안쪽/주둥이 같은 부위
  (`bearAccent`, `bearAccent_2`, `bearAccent_3` 등)도 나중에 별도 CSS 변수로
  뺄 수 있다. 지금은 고정 색(`#CCCCCC`)으로 둔다
- **표정 교체**: 눈/코/입이 캐릭터 SVG 안에 이미 별도 레이어로 분리되어
  있다 (`sealLeftEye`, `sealRightEye`, `bearNose`, `mochiLip` 등). 나중에
  윙크·하트눈 같은 표정 교체 기능을 붙일 여지가 있다는 뜻이지, 지금
  분리 작업이 더 필요하다는 뜻은 아니다
  - 이 경우 `items.category`에 `'face'`를 추가하면 되고, 테이블 구조
    변경은 필요 없다 (`category`는 이미 `hat` 외 확장을 염두에 두고
    만든 컬럼 — 4.5 참조)

## 4. 데이터 모델

### 4.1 인증

- **구글 로그인 (Supabase Auth, Google Provider).** 익명 인증 사용하지 않음
- 로그인 요청 시점 = **"저장하기" 클릭 시**
- `profiles` 로우는 최초 로그인 시 자동 생성
- 모든 유저 테이블에 RLS. **본인 것만 읽고 쓰기**
- Edge Function은 클라이언트가 보낸 `user_id`를 신뢰하지 않는다. **JWT에서 직접 꺼낸다**
- 포스터도 Supabase에 저장 (Postgres `posts` + Storage). IndexedDB 폐기 완료

### 4.2 테이블

```sql
-- 아이템 마스터 (관리자만 write)
items (
  id            text primary key,        -- 'hat_crown'
  name          text not null,           -- '왕관'
  category      text not null,           -- 'hat' (향후 'glasses','scarf' 확장 대비)
  rarity        text not null,           -- 'common'|'rare'|'legendary'|'hidden'
  is_colorable  boolean not null,
  svg_path      text not null,
  sort_order    int
)

-- 유저 보유 현황
user_items (
  id          uuid primary key,
  user_id     uuid references auth.users not null,
  item_id     text references items not null,
  color_hex   text,                                    -- 고정색 아이템은 null
  acquired_at timestamptz default now(),
  post_id     uuid references posts ON DELETE SET NULL, -- ★ 4.3 참조
  consumed_at timestamptz                              -- ★ 4.4 참조. 현재 항상 null
)
-- ★ unique 제약을 걸지 말 것. 같은 감투를 여러 번 받으면 여러 행이 쌓인다

-- 프로필
profiles (
  ...기존...
  main_character  text default 'bear',   -- 'seal'|'panda'|'bichon'|'bear'|'mochi'
  amaze_count     int  default 0,        -- 누적 감탄
  last_drop_date  date                   -- 미사용. 로직에서 참조하지 않음
)
```

### 4.3 `post_id` — 느슨한 연결 (중요)

**반드시 `ON DELETE SET NULL` 이어야 한다.**

- 이전 버전에서 이 설정이 빠져 있어, 감투가 나온 포스터를 삭제하면
  FK 위반(`23503`)으로 삭제가 실패하는 버그가 있었다
- 포스터는 유저의 것이고, 마음에 안 들면 언제든 지울 수 있어야 한다.
  이미 받은 감투 때문에 삭제가 막히면 안 된다
- 포스터를 지우면 `post_id`만 `null`이 되고 감투는 그대로 남는다
- 나중에 "이 감투를 받은 날의 포스터 보기" 기능을 붙일 경우,
  `post_id`가 `null`이면 "연결된 기록이 삭제됨"으로 처리한다

### 4.4 `consumed_at` — 미래를 위한 자리

- **현재는 항상 `null`이며 아무 기능도 없다**
- 나중에 중복 감투를 분해(→ 감탄 전환)하거나 교환하는 기능이 생길 때,
  소모된 아이템을 표시하기 위한 컬럼이다
- 지금 미리 넣어두는 이유: 나중에 추가하면 **이미 쌓인 아이템들의 상태를
  소급 처리**해야 해서 비싸다. 컬럼 하나 미리 두는 비용이 훨씬 싸다
- 조회 시 `consumed_at is null` 조건을 습관적으로 걸어둘 필요는 없다.
  기능이 생길 때 일괄 반영하면 된다

### 4.5 기타 설계 근거

- `color_hex`: 같은 비니라도 색이 다르면 도감에서 별개 슬롯으로 센다
- `main_character`는 **언제든 변경 가능**. 감투는 계정 귀속이라 캐릭터를 바꿔도 유지된다
- `category`: 향후 안경(눈 기준 앵커), 목도리(하단 앵커) 등 다른 앵커 카테고리 확장 대비.
  현재는 `hat`만 사용

## 5. 드랍 로직

### 5.1 판정 위치 — 반드시 서버

**Supabase Edge Function에서 판정하고 결과만 내려보낸다.**

- 클라이언트 `Math.random()`은 개발자 도구로 조작된다
- 무료 앱이라도 도감 완성률이라는 순위가 생기는 순간 조작 시도가 나온다

### 5.2 판정 순서

```
1. 사진 포함 여부 확인          (없으면 감투 없음, 감탄만 +1)
2. rarity 추첨                  (현재는 왕관 1종뿐이라 사실상 확정)
3. 해당 rarity 내에서 item 추첨
4. is_colorable == true 이면 색상 팔레트에서 추첨
5. user_items 에 insert         ← 중복 여부를 검사하지 않는다. 그냥 쌓는다
6. profiles.amaze_count += 1
7. 획득 결과 반환
```

**하지 말 것**

- 하루 횟수 제한 검사 (제거됨)
- 이미 보유한 조합인지 확인 후 재추첨 (**중복은 정상 동작이다**)
- `last_drop_date` 갱신 (미사용 컬럼)

### 5.3 확률 — **미정**

수치는 사용자와 협의 후 확정한다. 임의로 정하지 말 것.
구조상 원칙만 정해져 있다.

- `common`이 대부분을 차지해야 한다 (계속 나오는 맛)
- `hidden`은 1종만 존재하며 최상위다 (`hat_gamtoo` — 앱 이름과 동일)
- **감투 종류가 5~6종 이상 확보된 뒤에 정한다.** 1~2종 상태에서 확률을 정해봐야
  체감이 안 되므로 무의미하다

## 7. 감투 탭 — 도감 / 내 감투

`감투` 탭 하나 안에서 두 화면을 전환한다. 같은 데이터를
**종류로 보느냐 / 개수로 보느냐**의 차이다.

### 7.1 두 화면의 성격 (혼동 금지)

| | **도감** | **내 감투** |
|---|---|---|
| 기준 | 종류 | 개수 |
| 답하는 질문 | 무엇을 모았나 | 얼마나 쌓였나 |
| 중복 | 한 칸으로 합침 | **중복이 곧 성취** |
| 정렬 | 등급·카테고리순 | **획득 시간순 (최신 우선)** |
| 감정 | 완성 욕구 | 축적 욕구 |
| 비유 | 명예의 전당 | 매일 쌓이는 컬렉션 |

**둘 다 필요하다.** 도감만 있으면 왕관을 100개 받아도 화면이 한 칸이라
매일 기록하는 보람이 눈에 안 보인다. 반대로 보관함만 있으면
"무엇이 남았나"를 알 수 없어 수집 목표가 생기지 않는다.

### 7.2 도감

- 그리드. 1칸 = 모자 1형태
- 미획득: 실루엣 처리 (형태는 보이되 색 없음), 이름은 `???`
- 획득: 원래 색상 + **보유 개수 표시** (`왕관 ×3`)
- 상단에 완성률 (`1 / 12`)
- 상세보기: 메인 캐릭터가 그 감투를 쓴 모습, 이름, 등급, 최초 획득 일시
- 그리드에서 아이템은 약 80px로 작게 보인다. **실루엣만으로 구분 가능해야 한다.**
  새 에셋 추가 시 이 크기에서 먼저 확인할 것

### 7.3 내 감투

- **획득 시간순으로 쭉 나열.** 중복도 각각 한 칸을 차지한다
- 총 보유 개수를 크게 표시 (누적감이 핵심)
- 흔한 아이템이 이어지다가 중간에 희귀 아이템이 박혀 있는 리듬이 이 화면의 재미다.
  등급별로 묶어서 정렬하면 이 리듬이 사라진다. **반드시 시간순을 기본으로 할 것**
- 획득 일시 표시 (`07.26 14:32`)

### 7.4 향후 확장 (지금 만들지 말 것)

색상 랜덤 아이템이 들어오면 도감이 2층이 된다.

```
도감 1칸 = 모자 1형태
  └ 그 칸 안에 색상 슬롯 — "비니 5색 / 전체 14색"
```

- 색깔만 다른 100종을 100칸으로 나열하면 "다 못 채운다"는 느낌에 오히려 안 채운다
- 형태 단위로 100% 달성이 가능해야 하고, 색상은 그 안의 심화 목표로 둔다
- **지금 색상 슬롯 UI를 만들 필요는 없다.** 다만 데이터 구조와 컴포넌트를
  나중에 끼워 넣기 쉽게 짜둘 것

## 8. 결정 상태

> 이전 버전에서 AI가 임의로 "확정"이라 적어둔 항목들이 사용자 의사와 어긋난 사례가 있었다.
> 이번 버전은 **누가 결정했는지**를 구분해 표기한다.

### 8.1 사용자가 결정한 것 (변경하려면 반드시 사용자에게 확인)

- 재화 이름 = **감탄**, 수집품 = **감투**
- 메인 캐릭터는 유저가 선택하며 **언제든 변경 가능**. 감투는 계정 귀속
- **인증 = 구글 로그인.** 익명 인증 아님
- **로그인 요청 시점 = "저장하기" 클릭 시**
- **포스터 저장 = Supabase.** IndexedDB 폐기
- **하루 횟수 제한 없음.** 기록할 때마다 감투 지급
- **중복 획득 허용.** 쌓이게 두고, 나중에 분해/교환 여지를 남긴다
- **`post_id`는 느슨한 연결.** 포스터 삭제가 감투 때문에 막히면 안 된다
- **`감투` 탭 안에서 도감 ↔ 내 감투 전환.** 포스터 보관함은 별도 탭
- 에셋 규격 (3장 전체) — 실측 검증값

### 8.2 AI 제안 (사용자가 명시적으로 반대하지 않은 것 — 이견 있으면 사용자에게 확인)

- 드랍 판정은 서버(Edge Function)에서만
- 감투 지급 조건에 "사진 포함" 유지
- 유저 간 거래·교환 없음
- 등급 체계 4단계 (common / rare / legendary / hidden)
- 도감에 보유 개수 표시, 내 감투는 시간순 정렬

### 8.3 미정 (임의로 정하지 말 것)

- 등급별 드랍 확률 수치 → **감투 5~6종 확보 후 결정**
- 색상 팔레트 구성 및 개수
- 재질/희귀도의 시각적 표현 (무광 → 유광 → 홀로그램 등)
- **중복 감투의 용도** (분해 → 감탄 전환 / 원하는 감투와 교환 / 그냥 쌓아두기)
- **감탄의 소모처** (칭호, 해금 조건, 교환 재화 등)
- 뱃지·칭호 티어
- 도감 현황의 외부 공유 방식
- 디스코드 연동 여부

### 8.4 하지 말 것

- 아이템용 캐릭터를 **별도로 만들지 말 것.** 캐릭터는 세상에 한 벌만 존재해야 한다
- 캐릭터별 앵커 오프셋 테이블을 만들지 말 것. 불필요하다
- `user_items`에 unique 제약을 걸지 말 것. **중복은 정상 동작이다**
- 하루 횟수 제한을 되살리지 말 것
- 중복 획득 시 재추첨하지 말 것
- 유저 간 거래 기능을 만들지 말 것
- 유료 구매, 확률형 유료 뽑기를 만들지 말 것
  (게임산업법상 확률형 아이템 확률 공시 의무 및 사행성 이슈에 진입한다)
