# 감투 — 아이템 시스템 명세

> 이 문서는 감투 앱에 수집 요소를 추가하기 위한 설계 명세입니다.
> 작업 시작 전 전체를 읽고, 8장의 "확정 / 미정" 구분을 반드시 확인하십시오.
> **미정 항목은 임의로 확정하지 말고 사용자에게 질문하십시오.**

## 1. 현재 앱 현황 (이미 구현된 것)

- **앱 이름**: 감투 ("감탄 to me"의 줄임말)
- **한 줄 정의**: 하루의 작은 감탄을 기록하고 포스터로 남기는 앱
- **스택**: Next.js + Supabase + Vercel
- **주요 경로**
  - `/make` — 기록 생성. 사진(선택), 문구(선택, 40자), 위치(선택)
    - 문구 미입력 시 기본값 `I amaze myself.`
    - 위치 미입력 시 기본값 `Seoul, Myeong-dong`
  - `/archive` — 보관함. 생성된 포스터를 2열 그리드로 표시
- **기록 흐름**: 입력 → **축하 애니메이션** ("나에게 감탄!") → 포스터 완성 → 저장/다운로드
- **캐릭터**: 클레이 스타일 동물 얼굴 5종 (물범, 판다, 비숑, 아기곰, 모찌)
- **현재 캐릭터는 아이템 시스템에 연결되어 있지 않음**

## 2. 새로 만들 것과 그 이유

### 2.1 왜 만드는가

유저가 자기 자신을 칭찬하는 기록 앱에 **수집 요소**를 더해, 재방문 동기와 지속성을 만든다.
단, 이 앱의 본질은 자기칭찬(내적 동기)이므로, 보상이 **행동의 대가**가 아니라
**행동의 흔적(기념품)** 으로 읽히도록 설계해야 한다.

> 보상이 행동의 이유가 되면 안 되고, 행동의 증거여야 한다.

이 원칙을 어기면 보상이 시들해지는 순간 기록 자체가 멈춘다(과잉정당화 효과).

### 2.2 만들 것 4가지

| # | 항목 | 설명 | 이유 |
|---|---|---|---|
| 1 | **감탄** (재화) | 누적 카운터. 기록할 때마다 확정 지급 | "오늘 아무것도 못 받은 날"을 없애기 위함. 자기칭찬 앱에서 빈손 경험은 치명적 |
| 2 | **감투** (수집품) | 캐릭터가 쓰는 모자. 확률 드랍 | 수집 욕구를 담당. 희귀도가 있어야 지속됨 |
| 3 | **메인 캐릭터 선택** | 유저가 5종 중 1종을 고정 | "내 캐릭터"라는 애착이 있어야 자랑할 이유가 생김 |
| 4 | **도감 탭** | 보유 감투 현황. 보관함 옆에 배치 | 수집한 것을 볼 곳이 없으면 수집 시스템이 성립하지 않음 |

### 2.3 왜 재화와 수집품을 분리하는가 (중요)

하나로 합치면 반드시 실패한다.

- 희귀하게 만들면 → 안 쌓여서 누적감이 없음
- 쌓이게 만들면 → 안 희귀해서 수집욕이 없음

따라서 **2층 구조**로 분리한다.

- **1층 감탄**: 매번 확정 지급. 계속 쌓임. 나중에 등급/칭호의 근거가 됨
- **2층 감투**: 확률 드랍. 도감을 채움

### 2.4 삽입 위치

```
기록하기  →  축하 연출  →  포스터 완성  →  보관함 / 도감
 (기존)      (기존+드랍)      (기존)        (도감 신규)
```

**중요**: 새 화면을 만들지 않는다. 축하 애니메이션이 이미 존재하고
그 안에 클레이 왕관/꽃다발/리본이 흩날린다. 즉 **보상 연출 자리가 이미 있다.**
그 연출의 마지막에 "획득한 감투를 쓴 캐릭터" 1컷을 노출하는 방식으로 얹는다.

## 3. 에셋 규격 (확정 — 실측 검증 완료)

캐릭터 5종 + 모자 3종 SVG 파일을 직접 파싱해 검증한 값이다. **변경하지 말 것.**

### 3.1 공통 좌표계

```
viewBox : "0 -100 270 370"   ← 캐릭터/아이템 8개 파일 전부 동일
얼굴 원 : cx=135  cy=135  r=135
상단 여유: y = -100 까지 (모자가 얼굴 위로 솟는 공간)
```

### 3.2 합성 방법

**좌표 변환, 스케일 계산, 앵커 오프셋 테이블이 전부 불필요하다.**
캐릭터와 모자가 동일 viewBox를 공유하므로 그냥 겹치기만 하면 된다.

```jsx
<svg viewBox="0 -100 270 370">
  <CharacterSvg />   {/* 아래 레이어 */}
  <HatSvg />         {/* 위 레이어 — z-index 상위 */}
</svg>
```

- 모자가 귀나 더듬이를 일부 가리는 것은 **의도된 동작**이다. 보정하지 말 것
- 캐릭터별 개별 조정 로직을 만들지 말 것

### 3.3 파일 목록

**캐릭터** (`char_*.svg`)

| 파일 | 캐릭터 | id 접두어 |
|---|---|---|
| `char_seal.svg` | 물범 | `seal*`, `*S` |
| `char_panda.svg` | 판다 | `panda*`, `*P` |
| `char_bichon.svg` | 비숑 | `bichon*`, `*B` |
| `char_bear.svg` | 아기곰 | `bear*`, `*R` |
| `char_mochi.svg` | 모찌 | `mochi*`, `*M` |

**모자** (`hat_*.svg`)

| 파일 | 이름 | 색상 | 상단 y | 하단 y |
|---|---|---|---|---|
| `hat_beanie.svg` | 비니 | **변수형** | -83 | 42 |
| `hat_crown.svg` | 왕관 | 고정 | -86 | 42 |
| `hat_jokduri.svg` | 족두리 | 고정 | -56 | 40 |

### 3.4 SVG id 규칙 (필수)

- 모든 SVG의 gradient/filter id는 **파일 간 고유**해야 한다
- 현재 45개 id 전부 고유함이 검증됨. 중복 0
- **새 에셋을 추가할 때 반드시 접두어를 붙일 것** (`hat_gat.svg` → `gatBody`, `gatBrim`)
- 이유: 도감 그리드에 여러 캐릭터를 인라인 SVG로 동시 렌더하면,
  id가 겹칠 경우 브라우저가 문서 전체에서 첫 번째 정의를 찾아 쓴다.
  → 물범의 그라디언트가 아기곰에 적용되는 식으로 색이 깨진다

### 3.5 색상 변수 (변수형 모자 전용)

```css
--hat-base   /* 기본색 */
--hat-light  /* 밝은 면 */
--hat-dark   /* 어두운 면 */
```

- 각 변수에 폴백값이 이미 들어있어 변수 미주입 시에도 렌더된다
- 그라디언트 stop이 이 변수를 참조한다
- **모자는 반드시 인라인 SVG로 렌더해야 한다.** `<img src>` 나 CSS 배경으로 넣으면
  외부 CSS 변수가 주입되지 않아 색상 랜덤이 동작하지 않는다
- 색상 팔레트는 `base` 하나에서 `light` / `dark` 를 계산해 파생시키는 구조를 권장.
  그래야 색상 추가가 값 하나 넣는 것으로 끝난다

## 4. 데이터 모델 (Supabase)

### 4.0 인증 방식 (확정 — 2026-07-25 결정)

- **구글 로그인 (Supabase Auth, Google Provider).** 익명 인증은 쓰지 않는다.
  나중에 정식 계정 전환 시 "익명 → 정식 승격" 로직이 통째로 필요 없어지므로
  처음부터 구글 로그인으로 간다.
- **로그인은 앱 진입 시점이 아니라 "저장하기" 시점에 요청한다.**
  ```
  앱 진입 → /make 바로 사용 가능 (로그인 없이 포스터 생성)
  다운로드      → 로그인 없이 허용
  저장하기      → 이 시점에 구글 로그인 요청
  ```
  결과물을 먼저 보여준 뒤에 로그인을 요청해야 납득이 되고 이탈이 적다.
- `user_items.user_id references auth.users` 는 그대로 유효하다 — 구글 로그인 성공 시
  Supabase가 `auth.users` 로우를 실제로 만들어주므로 스키마 변경이 필요 없다.
- `profiles` 로우는 **최초 로그인 시 자동 생성**한다 (트리거 또는 첫 요청 시 upsert).
- 모든 유저 테이블(`user_items`, `profiles`, `posts`)은 RLS로 **본인 것만 읽고 쓰기**로 제한한다.
- 드랍 판정 Edge Function은 **클라이언트가 보낸 user_id를 신뢰하지 않는다.**
  요청의 JWT에서 직접 유저를 꺼내 쓴다.
- **포스터 저장소도 Supabase로 이관한다 (Postgres `posts` + Storage).** 브라우저 로컬
  IndexedDB는 폐기. `posts` 메타데이터는 서버, 이미지는 로컬로 쪼개두면 기기 간
  보관함이 안 맞고(로그인 개념과 앞뒤가 안 맞음), 나중에 옮길 때 또 고쳐야 한다.
  아직 실사용자가 없어 데이터 이관/유실 비용이 0인 지금이 가장 싼 시점이라
  Phase 1과 묶어 바로 처리한다.

### 4.1 테이블

```sql
-- 아이템 마스터 (관리자만 write)
items (
  id            text primary key,        -- 'hat_crown'
  name          text not null,           -- '왕관'
  category      text not null,           -- 'hat' (향후 'glasses', 'scarf' 확장 대비)
  rarity        text not null,           -- 'common' | 'rare' | 'legendary' | 'hidden'
  is_colorable  boolean not null,        -- 색상 랜덤 대상 여부
  svg_path      text not null,
  sort_order    int
)

-- 유저 보유 현황
user_items (
  id          uuid primary key,
  user_id     uuid references auth.users not null,
  item_id     text references items not null,
  color_hex   text,                      -- is_colorable=false 이면 null
  acquired_at timestamptz default now(),
  post_id     uuid references posts,     -- 어느 기록에서 나왔는지
  unique (user_id, item_id, color_hex)   -- 같은 색 중복 방지
)

-- 프로필 확장
profiles (
  ...기존...
  main_character text default 'bear',    -- 'seal'|'panda'|'bichon'|'bear'|'mochi'
  amaze_count    int  default 0,         -- 누적 감탄
  last_drop_date date                    -- 하루 1회 제한용
)
```

### 4.2 설계 근거

- `color_hex` 를 `user_items` 에 두는 이유: 같은 비니라도 색이 다르면 별개 수집품
- `unique` 제약: 같은 색 중복 획득 방지. 중복 시 다른 색을 뽑도록 재시도
- `post_id`: "이 감투는 그날의 기록에서 나왔다"는 연결. 나중에 도감에서
  획득 당시 포스터로 이동하는 기능의 근거가 됨
- `main_character` 는 **언제든 변경 가능**. 감투는 계정 귀속이므로
  캐릭터를 바꿔도 보유 감투는 유지된다
- `category` 를 지금 넣는 이유: 나중에 안경(눈 기준 앵커), 목도리(하단 앵커) 등
  다른 앵커 카테고리가 추가될 여지가 있음. 지금은 `hat` 만 사용

## 5. 드랍 로직

### 5.1 판정 위치 — 반드시 서버

**Supabase Edge Function 에서 판정하고 결과만 클라이언트로 내려보낸다.**

- 클라이언트에서 `Math.random()` 을 돌리면 개발자 도구로 조작된다
- 무료 앱이라도 도감 완성률이라는 순위가 생기는 순간 반드시 조작 시도가 나온다
- 나중에 서버로 옮기는 비용이 처음부터 서버로 만드는 비용보다 훨씬 크다

### 5.2 지급 조건

| 항목 | 규칙 | 이유 |
|---|---|---|
| **감탄** | 기록 저장 시 항상 +1 | 빈손 경험 방지 |
| **감투** | 사진이 포함된 기록만 | 완전히 빈 기록으로 파밍하는 것을 최소한으로 차단 |

**파밍 취약점 (실제 확인됨)**

현재 `/make` 는 사진·문구·위치가 전부 선택 사항이라 **아무것도 입력하지 않아도
기록이 생성된다.** 실제 보관함 데이터에서 같은 날짜 기록 4건이 확인되었다.
사진 조건 없이 보상을 붙이면 버튼 연타만으로 무한 획득이 가능해진다 — 그래서
"사진 포함" 조건은 유지한다.

**하루 1회 제한은 두지 않는다 (2026-07-26 결정).** 유저 수가 적은 지금은
사진이 포함된 기록을 여러 번 저장해 반복 획득하는 것 자체를 문제로 보지
않는다. 유저 규모가 커지면 재검토할 사안이며, **지금 시점의 제약으로는
쓰지 않는다.** `profiles.last_drop_date` 컬럼은 나중에 다시 쓸 가능성을 위해
스키마에는 남겨두되, 판정 로직에서는 더 이상 참조하지 않는다.

### 5.3 판정 순서

```
1. 하루 1회 제한 확인 (profiles.last_drop_date)
2. 사진 포함 여부 확인
3. rarity 추첨 → common / rare / legendary / hidden
4. 해당 rarity 내에서 item 추첨
5. is_colorable == true 이면 색상 팔레트에서 추첨
6. user_items 에 이미 있는 조합이면 → 다른 색/아이템으로 재추첨
7. insert + profiles 갱신 (amaze_count, last_drop_date)
8. 획득 결과 반환
```

### 5.4 확률 — **미정**

수치는 사용자와 협의 후 확정한다. 임의로 정하지 말 것.
다만 구조는 아래를 따른다.

- `common` 이 대부분을 차지해야 한다 (계속 나오는 맛)
- `hidden` 은 1종만 존재하며 최상위다 (아이템 id: `hat_gamtoo` — 앱 이름과 동일)

## 7. 도감 화면 구조

### 7.1 2층 구조 (중요)

색상 랜덤을 도입하면 아이템 수가 폭발한다. 이때 **색깔만 다른 100종을
100칸으로 나열하면 성취감이 오히려 떨어진다.** "다 못 채운다"고 느끼면 아예 안 채운다.

```
도감 1칸 = 모자 1형태          → 8~12칸. 도달 가능한 목표. 100% 달성 가능
  └ 각 칸 안에 색상 슬롯       → "비니 — 보유 5색 / 전체 14색". 무한 수집욕 수용
```

- 가볍게 하는 유저: 형태만 다 모아 도감 100% 달성 → 만족
- 깊게 파는 유저: 전 색상 컴플리트 도전 → 장기 목표
- 고정색 아이템(왕관/족두리/감투)은 슬롯이 1개뿐 → **획득 즉시 완성**. 자연히 무게가 실림

### 7.2 UI

- 위치: 보관함 탭 옆에 **도감 탭** 신규 추가
- 미획득 아이템은 실루엣 처리 (형태는 보이되 색은 없음)
- 도감 그리드에서 아이템은 작게(약 80px) 렌더된다.
  **실루엣만으로 구분 가능해야 한다.** 새 에셋 추가 시 이 크기에서 먼저 확인할 것

## 8. 확정 / 미정 구분

> **미정 항목을 임의로 확정하지 마십시오. 반드시 사용자에게 질문하십시오.**

### 확정

- 재화 이름 = **감탄**, 수집품 = **감투**
- 2층 구조 (감탄 = 누적 / 감투 = 수집)
- 메인 캐릭터는 유저가 선택하며 **언제든 변경 가능**. 감투는 계정 귀속
- **유저 간 거래·교환 없음.** 한 번 열면 되돌릴 수 없고,
  거래가 생기면 파밍 어뷰징이 필연적으로 따라온다
- 드랍 판정은 **서버(Edge Function)** 에서만
- 지급 조건: 사진 포함 (하루 1회 제한 없음 — 5.2, 2026-07-26 결정)
- 에셋 규격 (3장 전체)
- 도감 2층 구조
- **인증 방식 = 구글 로그인 (Supabase Auth Google Provider), 익명 인증 아님** (4.0)
- **로그인 요청 시점 = "저장하기" 클릭 시.** 앱 진입/포스터 생성/다운로드는 로그인 불필요 (4.0)
- **포스터 저장 = Supabase(Postgres `posts` 테이블 + Storage).** 브라우저 로컬 IndexedDB는 폐기.
  아직 실사용자가 없어 이관 비용이 가장 쌀 때 정리함 (4.0)

### 미정

- 등급별 드랍 확률 수치
- 색상 팔레트 구성 및 개수
- 재질/희귀도의 시각적 표현 (무광 → 유광 → 홀로그램 등)
- 뱃지·칭호 티어 (감탄 누적 몇 회에 무엇을 줄 것인가)
- 도감 현황의 외부 공유 방식
- 디스코드 연동 여부

### 하지 말 것

- 아이템용 캐릭터를 **별도로 만들지 말 것**. 캐릭터는 세상에 한 벌만 존재해야 한다
- 캐릭터별 앵커 오프셋 테이블을 만들지 말 것. 불필요하다
- 유저 간 거래 기능을 만들지 말 것
- 유료 구매, 확률형 유료 뽑기를 만들지 말 것
  (게임산업법상 확률형 아이템 확률 공시 의무 및 사행성 이슈에 진입한다)

## 9. Phase 1 작업 범위

**목표: 감투 1종(왕관)만으로 전체 파이프라인을 끝까지 관통한다.**

에셋을 다 만든 뒤 코드에 붙이면, 문제를 발견하는 시점이 이미 늦다.
1종으로 뚫어놓으면 나머지는 파일 추가만으로 끝난다.

### 체크리스트

- [x] Supabase 테이블 생성 (`items`, `user_items`, `profiles` 확장)
- [x] `items` 에 왕관 1건 시드
- [x] 메인 캐릭터 선택 UI (최초 진입 시 1회, 이후 설정에서 변경) — `/profile`
- [x] 캐릭터 + 모자 인라인 SVG 합성 컴포넌트 — `CharacterWithHat`
- [x] 드랍 판정 Edge Function (Phase 1 은 확정 지급으로 시작해도 무방) — `supabase/functions/drop-item`, 서버(JWT 기반) 판정으로 처음부터 구현
- [x] **감탄(1층) 카운터 UI — 최초 체크리스트에서 누락됐던 항목.** `profiles.amaze_count`는
      기록 저장마다(사진 유무 무관) 항상 +1 되도록 Edge Function에 이미 있었지만,
      화면에 노출하는 항목이 빠져 있었다. 저장 완료 화면에 "감탄 +1" 피드백,
      도감/내 캐릭터 탭에 누적 수치 노출로 보완
- [x] 축하 애니메이션 마지막에 획득 캐릭터 1컷 노출 — 단, 2.4장 원래 그림과 달리
      실제로는 "저장하기" 성공 직후에 뜬다 (감투는 `post_id`가 있어야 하는데,
      로그인 게이트 도입 이후 `post_id`는 저장 성공 시점에야 생기기 때문)
- [x] 도감 탭 신규 추가. 미획득 실루엣 처리 — `/collection`
- [x] 도감 그리드 80px 크기에서 실루엣 판별 확인 — `/dev/items`에서 확인 완료

### 이후 Phase

- **Phase 2** — 감투 종류 확장, 색상 랜덤, 희귀도/재질, 스트릭 전용 감투, 도감 완성률 %
- **Phase 3** — 도감 현황 이미지 카드 내보내기(기존 포스터 생성 로직 재활용),
